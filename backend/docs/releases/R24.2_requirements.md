# R24.2 — Lifecycle Alerts + Richer Actionable Details + Dashboard Workflow

## Objective

Deliver actionable, contract-specific lifecycle alerts for options and shares, surfaced in the dashboard and Slack, with structured (no-prose) lifecycle evaluation output, severity-based ordering, and strict non-regression of decision-artifact hygiene and determinism.

## Non-negotiables (must not regress)

- Decision JSON artifacts remain code-only. Canonical `out/decision_latest.json` and archived history only.
- Never persist prose/UI strings/panels or raw FAIL_/WARN_ in decision artifacts.
- UI must never display raw FAIL_/WARN_; API must not return them in UI payloads.
- SDLC gates (pytest, frontend test, frontend build) must pass; raw outputs pasted in `out/verification/R24.2/notes.md`.
- Repo hygiene: `out/` whitelist only; no secrets; no scratch.
- Deterministic behavior: universe evaluation vs per-symbol recompute must match under snapshot semantics.

## Scope

### Backend

- **A) Lifecycle evaluation output (structured, request-time only)**  
  For each actionable item (options + shares): symbol, strategy; options: expiry, strike, dte, entry_credit, current_price_proxy (numeric/structured), pct_max_profit (when computable), size, notional; next_action (safe label only: ENTRY/HOLD/CLOSE/ROLL/NONE); next_action_details (structured fields only, request-time only, never stored in decision artifacts); severity (high/medium/low); recommended_by (e.g. ruleset version string). No prose persistence.

- **B) Lifecycle rules (conservative, explainable)**  
  - PROFIT_TARGET_HIT / target hit: close/take profit when target reached (existing exit_plan/targets_already_exceeded logic).  
  - ROLL_WINDOW: when DTE ≤ N (e.g. 14) and position open; explainable via dte, extrinsic_proxy when available.  
  - RISK_BREACH / stop hit: deterministic using existing support/stop levels.  
  - Shares: EXIT_SIGNAL / TARGET_HIT from existing shares trade plan and exit_plan logic.  
  - Modes: conservative defaults only; no gambling rules.

- **C) API**  
  Extend GET `/api/ui/action-needed` to return enriched actionable details and lifecycle state (severity, contract fields for options). Response must contain no raw FAIL_/WARN_ strings; only safe labels.

- **D) Slack**  
  Actionable Slack message includes contract-specific fields (symbol, strategy, expiry, strike, dte, premium/size, next action, rationale). Dedupe unchanged (`chakraops/data/slack_actionable_dedupe.json`). No spam.

### Frontend

- **E) Dashboard**  
  Daily command center: group or sort Action Needed by severity (high first) and show enriched details inline. Deep links open correct tab and accordion (existing). UI shows safe labels only (no raw codes).

## Non-scope

- No new brokers or auto-execution.
- No persistence of next_action_details or lifecycle prose in decision store.
- No in-app notifications store (optional later); Slack + action-needed API only for this release.

## API changes

- GET `/api/ui/action-needed`: extend each item in `top_options` / `top_shares` with: `severity` (high | medium | low), optional `expiry`, `strike`, `dte`, `size`, `notional`, `pct_max_profit` (options); `recommended_by` (string) when applicable. Existing fields unchanged. Response must not contain FAIL_/WARN_.

## UI changes

- Dashboard Action Needed: sort/group by severity (high first); display severity indicator; enriched fields (e.g. DTE, strike) where present. Deep link and safe labels only.

## Data model

- No new persisted tables or decision fields. Lifecycle and next_action_details remain request-time only. Severity derived from next_action_code (CLOSE/ROLL → high; ENTRY → medium; HOLD/NONE → low).

## Lifecycle rules (summary)

- **PROFIT_TARGET_HIT / TARGET_HIT:** Use existing targets_already_exceeded and t1 vs spot; next_action = CLOSE.  
- **ROLL_WINDOW:** DTE ≤ threshold (e.g. 14), position open → next_action = ROLL.  
- **Stop / RISK_BREACH:** Stop level vs spot → CLOSE.  
- **Shares:** Same as options for target/stop from shares_plan and exit_plan.

## Determinism requirements

- Universe run vs per-symbol recompute for the same symbol under the same snapshot must yield identical next_action_code and key computed fields used for lifecycle (e.g. severity). Snapshot semantics as in R22.7/R24.1.

## Test plan

- **Backend:**  
  - Assert GET `/api/ui/action-needed` (and symbol-diagnostics) response JSON contains no substring matching `FAIL_` or `WARN_`.  
  - Determinism: same snapshot → same lifecycle classification and key fields for a symbol.  
  - Assert next_action_details (and any lifecycle-only fields) are not written to `out/decision_latest.json`.  
  - Slack: required fields and no forbidden substrings (existing R24.1 tests); extend if new fields added.

- **Frontend:**  
  - Dashboard renders action items with severity and does not render raw FAIL_/WARN_.  
  - Deep link still opens correct accordion; no regression.
