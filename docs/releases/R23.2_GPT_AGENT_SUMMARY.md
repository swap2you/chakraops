# R23.2 — Complete Implementation Summary (for GPT Agent)

**Release:** R23.2 — Delta Transparency + Near-Miss Workflow + Optional Delta Override (Advanced) + Gate Code Persistence Tightening  
**Repo:** ChakraOps  
**Date:** 2026-02

This document is a single reference for any GPT agent working in the ChakraOps repo. It describes what R23.2 implemented, where it lives, and how it behaves.

---

## 1. High-level goals

- **Decision JSON stays code-only:** No prose, no raw `FAIL_*`/`WARN_*` strings, no UI-style gate "name" in persisted artifacts.
- **Delta reject transparency:** When a symbol is rejected due to delta band (e.g. WMT), operators see the actual best delta that missed the band, the miss magnitude, and direction (below/above band), plus a best-candidate snapshot.
- **Near-miss workflow:** If the miss is within a small epsilon (e.g. 0.02), the system adds a code-only reason `DELTA_NEAR_MISS` so operators can consider an override without changing verdict logic.
- **Optional delta override (advanced):** Operators can widen the delta band per symbol within a hard cap; overrides are stored in a config file (not in decision JSON), exposed via API and UI behind an "Advanced" toggle.
- **Gate persistence tightening:** Persisted gates use only `gate_code` (e.g. `STOCK_QUALITY_STAGE1`) and `status`; human-readable labels are derived at request time in the API.

---

## 2. Non-negotiables (constraints that must stay true)

1. **Decision JSON artifacts** (`out/decision_latest.json` and archived `decision_*.json`):  
   Code-only. No prose, no UI strings, no raw `FAIL_*`/`WARN_*` in persisted output. Gates: only `gate_code` + `status` (no `name`, no `reason`).
2. **UI:** Never displays raw `FAIL_*`/`WARN_*` codes; all reason/gate text is safe, human-readable labels derived from codes.
3. **SDLC gate:** Backend pytest, frontend `npm run test -- --run`, and `npm run build` must pass; results recorded in `out/verification/R23.2/notes.md`.
4. **Repo hygiene:** `out/` contains only whitelisted artifacts; no secrets; delta overrides live under `chakraops/data/`, not `out/`.

## 3. What was implemented (by part)

### Part 1 — Gate code persistence (code-only)

- **Persistence (`to_dict_persist`):**  
  For each gate in `gates_by_symbol`, only `gate_code` and `status` are written.  
  `gate_code` must match `^[A-Z0-9_]+$` (e.g. `STOCK_QUALITY_STAGE1`, `OPTIONS_LIQUIDITY_STAGE2`, `DELTA_BAND`, `ORATS_SUMMARY`).  
  No `name`, no `reason` in the persisted JSON.
- **Loader (`from_dict`):**  
  Backward compatible: if the file has `gate_code`, use it and set in-memory label via `gate_code_to_label()`; if it only has legacy `name`, map to `gate_code` via `gate_name_to_code()` (unknown names → `UNKNOWN_GATE`).
- **API (symbol-diagnostics):**  
  Gate list returned to the UI uses `gate_code_to_label(gate_code)` so the UI sees safe English labels (e.g. "Stock quality (Stage 1)") at request time only; the artifact on disk never stores those strings.

**Key symbols:**  
`gate_name_to_code()`, `gate_code_to_label()`, `GateEvaluation.gate_code`, `to_dict_persist()` (with internal `gate_persist()` for each gate).

---

### Part 2 — Delta transparency (request-time only)

- **When:** A symbol is rejected in Stage 2 due to delta (no contract within the target delta band). The backend builds **delta diagnostics at request time** when serving symbol-diagnostics; nothing is persisted in the decision artifact.
- **Delta diagnostics object (API):**  
  Returned only when there is a delta reject (sample of rejected contracts + band). Fields:
  - `band_min`, `band_max` — target delta band (e.g. 0.20–0.40).
  - `best_delta` — absolute delta of the closest candidate to the band.
  - `miss` — numeric distance to the nearest band edge (0 if inside).
  - `direction` — `"BELOW_BAND"` | `"ABOVE_BAND"` | `"IN_BAND"` (code-only in backend).
  - `best_candidate` — snapshot: `strike`, `expiry`, `bid`, `ask`, `spread_pct` (numbers only; no prose).
- **UI:**  
  On the Symbol (Execution Console) page, Options tab: when `delta_diagnostics` (or `delta_override`) is present, a **"Delta band (rejected)"** card is shown with:
  - Allowed band, best_delta, miss, and direction rendered as safe text ("below band" / "above band" / "in band").
  - A row for the closest contract (strike, expiry, bid, ask).
  - This is informational only; it does not change eligibility logic.

**Key symbols:**  
`_build_delta_diagnostics_at_request_time()` in `ui_routes.py`; `DeltaDiagnostics` in frontend types; direction values `BELOW_BAND`, `ABOVE_BAND` (replacing previous TOO_LOW/TOO_HIGH in this flow).

### Part 3 — Near-miss detection + optional delta override (advanced)

**Config (backend):**

- `DELTA_NEAR_MISS_EPS = 0.02` — If rejected due to delta and `miss <= EPS`, add `DELTA_NEAR_MISS` to `primary_reason_codes` (code-only). Verdict remains HOLD/BLOCKED; no auto-ELIGIBLE.
- `DELTA_OVERRIDE_MAX_WIDEN = 0.05` — Hard cap: a per-symbol override cannot widen the canonical band by more than this on either side.

**Near-miss (code-only):**  
In `evaluation_service_v2`, when building the symbol summary, if `REJECTED_DUE_TO_DELTA` is in `primary_reason_codes` and the first sample’s miss ≤ `DELTA_NEAR_MISS_EPS`, append `DELTA_NEAR_MISS` to `primary_reason_codes`. Verdict and eligibility logic are unchanged.

**Override storage:**

- File: `chakraops/data/delta_overrides.json` (NOT under `out/`).
- Format: `{ "SYMBOL": { "delta_lo": number, "delta_hi": number, "updated_at_utc": "ISO8601" } }`.
- Overrides are validated: must be within `DELTA_OVERRIDE_MAX_WIDEN` of the canonical band (e.g. canonical 0.25–0.35 → override allowed in [0.20, 0.40]); invalid ranges or exceeding max_widen are rejected.
- Overrides are **not** stored in the decision JSON; they only affect evaluation (Stage-2 delta band check).

**Evaluation integration:**  
In `staged_evaluator`, before running Stage-2 for a symbol, the code calls `get_effective_delta_band(symbol, canonical_lo, canonical_hi, max_widen)`. If an override exists and is valid, Stage-2 uses the overridden band; otherwise the canonical band is used.

**API:**

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/ui/delta-overrides` | List all per-symbol delta overrides. |
| POST | `/api/ui/delta-overrides/{symbol}` | Set override for symbol. Body: `{ "delta_lo": number, "delta_hi": number }`. Validated against canonical band and max_widen. |
| DELETE | `/api/ui/delta-overrides/{symbol}` | Remove override for symbol. |

**Symbol-diagnostics response:**  
When an override exists for the requested symbol, the response includes `delta_override: { delta_lo, delta_hi, updated_at_utc }` so the UI can show the "Override active" badge and prefill the advanced form.

**UI (advanced):**

- The Delta band card (when delta_diagnostics or delta_override is present) includes:
  - **"Override active"** badge and displayed override band when `delta_override` is set.
  - A **"Show Advanced" / "Hide Advanced"** toggle. Only when **Show Advanced** is on:
    - **"Adjust delta band (Advanced)"** section is visible with inputs for delta_lo/delta_hi and **Save** / **Reset** override.
- Override controls are intentionally gated so only advanced users change the band.

**Key symbols:**  
`delta_overrides.py` (load/save/delete, `get_effective_delta_band`), `trade_rules.DELTA_NEAR_MISS_EPS`, `trade_rules.DELTA_OVERRIDE_MAX_WIDEN`, `evaluation_service_v2` (DELTA_NEAR_MISS append), `staged_evaluator` (get_effective_delta_band before Stage-2), `ui_routes` (delta-overrides endpoints + delta_override in symbol-diagnostics).

## 5. Data shapes (for agents)

**Persisted gate (decision JSON):**  
`{ "gate_code": "STOCK_QUALITY_STAGE1", "status": "PASS" }` — no `name`, no `reason`.

**Delta diagnostics (API only, not persisted):**  
`{ "band_min": number, "band_max": number, "best_delta": number, "miss": number, "direction": "BELOW_BAND"|"ABOVE_BAND"|"IN_BAND", "best_candidate"?: { "strike", "expiry", "bid", "ask", "spread_pct" } }`.

**Delta override (API + file):**  
`{ "delta_lo": number, "delta_hi": number, "updated_at_utc"?: string }` per symbol. File: `chakraops/data/delta_overrides.json` as `{ "SYMBOL": { ... } }`.

**Symbol-diagnostics response (relevant R23.2 fields):**  
May include `delta_diagnostics` (when delta reject) and `delta_override` (when override exists for that symbol). Gates in the response use labels derived from `gate_code` at request time.

## 6. Grep / hygiene checks

- **No prose/FAIL_/WARN_ in new decision JSON:**  
  For a freshly written `out/decision_latest.json`,  
  `grep -E "FAIL_|WARN_|Stock qualified|Chain evaluated|Exit plan not computed|Not evaluated" out/decision_latest.json`  
  should yield no matches (code-only output). Legacy snapshots under `out/snapshots/` may still contain old format.
- **Gates code-only:**  
  `grep -E '"name"\s*:' out/decision_latest.json`  
  should have no matches in gates (new persists use `gate_code` only). Archived snapshots may still have `"name"`.
