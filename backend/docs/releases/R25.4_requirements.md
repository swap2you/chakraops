# R25.4 — Phase 4 Notifications Overhaul (Requirements)

## Scope

Stateful inbox (NEW → ACKED → ARCHIVED), filters, dedupe hygiene, actionable payload parity, and System Health integration. Notifications already exist (in-app page + JSONL store); R25.2 added SHARES_EXIT_SIGNAL, R25.3 added OPTIONS_* lifecycle (R25.3.1 moved emission to eval/scheduler). This release focuses on operator workflow, anti-spam, and reliability.

## Non-negotiables

- **Decision artifacts remain code-only** — No prose/UI strings or raw FAIL_/WARN_ in decision_latest.json.
- **UI** — Never display raw FAIL/WARN; use safe labels only.
- **Determinism** — Same inputs → same notification decisions (especially dedupe/transition).
- **Gates** — Backend pytest, frontend tests, frontend build pass; evidence in `out/verification/R25.4/notes.md`.

## Requirements

### 1) Notification state workflow

- States: **NEW** → **ACKED** → **ARCHIVED** (existing; ensure consistent).
- API: ack/archive single (existing) + **bulk** (ack all NEW, archive all ACKED).
- Response fields: `created_ts` (or timestamp_utc), `acked_ts` (when acked), `archived_ts` (when archived), `updated_ts`.

### 2) Actionability

- Each notification carries minimum structured fields to act without hunting:
  - **symbol**
  - **Options:** contract_key, expiry, strike, right, dte, profit_pct, mark_value (if available), recommended_action_code (CLOSE/ROLL/HOLD) when relevant.
  - **Shares:** hit_type, last_price, target/stop, recommended_action_code when relevant.
- Safe **title** and **summary** (no FAIL/WARN); avoid long prose.

### 3) Dedupe and anti-spam

- **Transition-aware dedupe:** one notification per (entity_key, event_type) while **active** (NEW or ACKED); re-trigger only after ARCHIVED or clear→retrigger transition. No time-window-only dedupe for actionable types.
- **Options lifecycle:** entity_key = contract_key; event_type = OPTIONS_PROFIT_TARGET_HIT | OPTIONS_ROLL_WINDOW | OPTIONS_ASSIGNMENT_RISK. Do not create a new one if an active (NEW or ACKED) notification exists for same (contract_key, event_type).
- **Shares exit:** entity_key = symbol + hit_type; do not create if active (NEW or ACKED) for same (symbol, hit_type).
- Deterministic logic.

### 4) UI inbox

- UI already had tabs/search; R25.4 adds bulk actions + deep links + health card.
- Notifications page: tabs/filters **NEW** / **ACKED** / **ARCHIVED** (and optionally ALL); search by symbol, type.
- Quick actions: Ack, Archive per row (existing).
- Bulk: “Ack all NEW”, “Archive all ACKED” (or “Archive all” for current tab).
- Each card: concise actionable fields + **deep link** to Symbol Diagnostics (tab=options/shares, accordion if supported).
- No FAIL/WARN anywhere in DOM.

### 5) System Health integration

- **Notifications Health** block in System Diagnostics / system-health:
  - last_emitted_ts (or latest notification created_ts)
  - count NEW, count ACKED, count ARCHIVED
  - Safe labels only.

## Out of scope

- Changing decision artifact schema or persistence.
- New notification types beyond existing (ORATS, scheduler, SHARES_EXIT_SIGNAL, OPTIONS_*).
- Slack payload changes (separate from inbox).
